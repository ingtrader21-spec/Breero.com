## Executive conclusion

BREERO has a substantial FastAPI/PostgreSQL test and migration foundation, but the API is not complete as a marketplace contract and is not production-ready.

The safe next action is not a repository-wide “fix all” sweep. The repository has a long stacked API program and several older overlapping refactor branches. Changes must be delivered as dependency-safe slices, with exact-head tests and review after every parent merge.

## Contract basis

The supplied BREERO architecture defines:

- one FastAPI `/api/v1` platform for public, client, provider and administrator surfaces;
- separate identity, catalog, geography, timezone, provider, scheduling, capacity, booking, matching, dispatch, trust, communications and platform domains;
- thin routers calling authorization and application/domain services;
- PostgreSQL/PostGIS as the authoritative source for booking, capacity, hold, assignment, authorization and lifecycle correctness;
- separate booking-intent and submitted-booking aggregates;
- dependency-ordered delivery;
- an endpoint-complete standard covering schemas, authentication, authorization, ownership/tenant scope, validation, transactions, error mapping, OpenAPI and tests.

This audit treats those requirements as target state. A documented route is not marked implemented unless it exists on the audited Git head with its owning behavior and tests.

# 4. Highest-impact concrete defects

## P0 — Target API stack is not on protected `main`

PRs #68 and #85–#88 contain migrations `018` through `022` and target identity/provider/booking/geography/provider-catalog APIs, but none is merged.

**Required correction:** stop extending the stack, review and merge each parent in order, retarget the child and rerun exact-head CI after every merge.

## P0 — Browser E2E does not certify the real API workflow

`apps/web/playwright.config.ts` starts Next.js with mock API mode unless `E2E_BASE_URL` is supplied. The required frontend workflow invokes the default command and does not supply a real API environment.

Browser success therefore proves UI behavior against mocks, not:

```text
Next.js → FastAPI → PostgreSQL/PostGIS → Redis/Celery
```

**Required correction:** add `ci/real-api-e2e-certification` with isolated PostGIS, Redis, API and web plus deterministic disabled/fake external adapters. Keep mock E2E as fast UI coverage.

## P0 — Canonical OpenAPI is environment-dependent

`apps/api/app/api/v1/router.py` omits route families when feature settings are false. `generate_openapi.py` imports the mounted app and serializes the resulting environment-specific surface.

**Impact:** runtime routes, `openapi.json`, API inventory and frontend contract checks can disagree.

**Required correction:** create `refactor/api-contract-determinism` and choose one explicit policy:

1. register stable routes and fail closed inside operations; or
2. generate named deterministic contract profiles with explicit inputs.

## P0 — Complete endpoint policy registry is absent on `main`

The OpenAPI generator validates operation-ID presence and uniqueness but does not require each operation to declare owner, audience, auth, permission, tenant scope, record policy, capability, idempotency/version, PII, rate limit and emitted event.

PR #62 proposes this on an older stack.

**Required correction:** rebuild that control on the final accepted foundation as `refactor/api-runtime-policy-registry-v2`.

## P1 — Target and legacy namespaces diverge

Target:

```text
/api/v1/messages/*
```

```text
/api/v1/operations/*

```

**Required correction:** create a compatibility ADR mapping legacy route, new route, shared service, response compatibility, deprecation metadata, consumer migration and removal gate. Do not perform a destructive rename.

## P1 — Readiness is hard-coded to migration 017

`apps/api/app/main.py` hard-codes `EXPECTED_SCHEMA_REVISION = "017_provider_credentials"`.

**Required correction:** bind expected schema identity to an immutable release/build manifest and define compatible application/database revision ranges while keeping readiness fail closed.

## P1 — V1 and V2 errors are transitional

V2 has a stable correlated error contract. V1 retains existing FastAPI/domain variants. The target architecture proposes a common envelope, but a broad V1 rewrite would be breaking.

**Required correction:** document current V1 variants, standardize headers and introduce envelope changes only through versioned or per-route migration with generated client evidence.

## P1 — Frontend contract check is a subset

`scripts/check-frontend-openapi.mjs` verifies selected public/customer routes and forbidden payment mutations. It does not certify every endpoint, permission, page/API mapping or provider/admin surface.

**Required correction:** retain the release-safety subset and add generated-client plus page/API ownership coverage. Do not describe the subset as complete API certification.

## P1 — API inventory is not bound to a runtime profile

`docs/backend-api-inventory.md` claims fixed path/operation totals and marks capability-dependent routes present. The README describes a Stripe-confirmed-booking slice while release flags intentionally disable payments and automatic confirmation.

**Required correction:** generate inventory from exact OpenAPI and embed source SHA, schema revision, contract profile, capability snapshot and counts. Distinguish implemented, mounted, enabled and production-certified.

## P2 — Prospective hardening: explicit mandatory skip count

Backend CI supplies a PostgreSQL URL and explicitly runs the mandatory integration and concurrency suites. No current mandatory test was shown to skip in that workflow. An explicit zero-skip counter would be prospective hardening.

**Optional hardening:** add a mandatory-suite zero-skip counter with named, documented environment exclusions.

Historical audit checkout cleanliness and exact-head CI/review evidence were not recorded; the machine-readable `git_state_recorded` flag is false.

## P1 — Node runtime target is unresolved

Repository metadata does not declare a Node engine. CI uses Node 22, while the supplied target architecture names Node 24 LTS.

**Required correction:** use the dedicated runtime-certification workstream to align package metadata, CI, Docker and documentation only after install, native dependency, build and browser tests pass.

## P2 — Root API/test memory was missing

No root agent/repository map existed. Backend and frontend configs were valid but distributed.

**Resolved here:** added `AGENTS.md`.

## P2 — Duplicate dependency declaration

`apps/api/pyproject.toml` lists Alembic twice.

**Required correction:** remove it in a dependency-only cleanup and rerun install, migrations and image gates.

# 6. Definition of API complete

A route is complete only when all applicable evidence exists:

```text
method/path
request/response schemas
stable operation ID
authentication and permission
tenant/legal-entity and record scope
capability policy
input/domain validation
transaction boundary
idempotency and request hash
concurrency/version policy
error mapping and required headers
rate limit and PII classification
audit and outbox/inbox
OpenAPI and generated client
unit and PostgreSQL/PostGIS integration tests
negative authorization tests
concurrency/replay tests
frontend contract/E2E where consumed
migration and rollback/forward-fix evidence
```

# 7. Audit limitations

This audit did not run code locally, access a server, mutate a database, merge a PR, activate a capability or verify DNS/TLS/Caddy/Kong. Follow-on implementation must use current exact-head CI rather than treating this report as test execution.
